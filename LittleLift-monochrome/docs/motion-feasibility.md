# Personal motion replay feasibility — 15 October 2026

**Build 6 decision:** free-signing support is confirmed for the main Watch app and its launcher. A three-minute, explicitly opt-in capture/replay prototype is now implemented and installed. Wrist-down continuity, battery cost and useful repetition accuracy remain unvalidated, so it stays outside ordinary logging. The Build 5 isolated probe evidence below is retained as historical context.

## What was actually established

The separate [`Experiments/MotionProbe`](../Experiments/MotionProbe) target imports Core Motion, Core ML and HealthKit and type-checks creation of a strength-training workout session. It builds for the installed watchOS 27 SDK with the existing free Personal Team. The generated seven-day profile includes `com.apple.developer.healthkit = true`, covers the registered devices, and the code signature verifies. The probe uses its own bundle identity and has not been installed. It requests no authorization, starts no workout, creates no samples and loads no model. At that Build 5 stage Little Lift's bundle identifiers, capabilities and private refresh script were untouched. Build 6 adds HealthKit and workout-processing only to the opt-in Watch capture path; identifiers/signing and the refresh script are preserved. No paid enrollment or distribution occurred.

Evidence is local and ignored: `BuildLogs/motion-probe-signing.log` and `.verification/observations/motion-signing-result.json`. Xcode's installed capability metadata also lists HealthKit under `XCODE_FREE_PROGRAM`. This agrees with Apple's current [watchOS capability table](https://developer.apple.com/help/account/reference/supported-capabilities-watchos), whose HealthKit row includes the free Apple Developer column. We inspected the table's actual checkmark markup because text-only extraction loses it. Do not repeat older blanket claims that HealthKit always requires paid membership.

## Capture and execution

[Core Motion](https://developer.apple.com/documentation/coremotion/) exposes acceleration, rotation and orientation. It describes the Watch's movement, not external load, the whole body's technique, or medical readiness. The wrist may barely move in some exercises, and unrelated movements can look like repetitions. Begin with deliberately selected movements and the user's stated exercise; broad recognition is not established.

Apple documents [HKWorkoutSession background execution](https://developer.apple.com/documentation/healthkit/running-workout-sessions) through lowered wrists and switching apps. It requires HealthKit setup, relevant user authorization and the workout-processing background mode. A flag or active foreground timer alone does not grant that execution. Excessive background CPU can still suspend or terminate an app. Ordinary logging still uses persisted rest deadlines and notifications. Only an explicitly started experiment creates its own HKWorkoutSession.

[Background refresh tasks](https://developer.apple.com/documentation/watchkit/background-execution) provide short execution opportunities, not a continuous sensor recorder. [Extended runtime sessions](https://developer.apple.com/documentation/watchkit/using-extended-runtime-sessions) are limited to specific use cases and durations: self-care 10 minutes, mindfulness one hour, physical therapy one hour, smart alarm 30 minutes. Their type must match the actual activity; treating an ordinary lifting workout as physical therapy would not establish an appropriate reliable solution.

Apple's [Core Motion session](https://developer.apple.com/videos/play/wwdc2023/10179/) documents CMMotionManager streams up to the hardware's supported rate, and batched streams on supported Watch hardware at 200 Hz device motion / 800 Hz acceleration delivered in one-second batches. CMBatchedSensorManager requires an active HealthKit workout session. Those rates are API options, not measured results on this Watch and not a requirement for this proposed feature. Check availability at runtime.

## Battery, data and local models

For a later opt-in pilot, a **25–50 Hz starting range is a hypothesis**, not a tested minimum or battery promise. Record actual sensor timestamps and gaps; the requested interval is not a guarantee. [Apple's update-interval guidance](https://developer.apple.com/documentation/coremotion/cmmotionmanager/devicemotionupdateinterval) explicitly calls for checking delivered timestamps. Stop collection promptly, buffer bounded chunks, avoid per-sample SwiftUI updates and postpone heavier processing to the phone. No GPS, audio, clinical records or unrelated health reads are needed for a wrist timing experiment.

An active HealthKit workout has additional sensor/runtime costs and may generate Health samples. Before any runtime prototype, disclose those effects, verify permissions and save/discard semantics, and examine the user's Health/iCloud settings so a local-only promise is accurate. The capability probe avoids all of those runtime side effects. Battery percentage, thermal behavior, CPU usage and missing-sample rates have not been measured. A simulator cannot provide that evidence.

[Core ML](https://developer.apple.com/documentation/coreml) supports local model execution without a server. [Create ML's activity classifier](https://developer.apple.com/documentation/createml/mlactivityclassifier) trains on real motion recordings and evaluates against recordings separate from training/validation. A class prediction is not automatically a repetition counter or a set boundary. No model was trained, and no synthetic samples are being passed off as personal training data.

A future pilot should retain raw timestamps, estimated boundaries and explicit user corrections separately. Train on locally collected, consented, labelled personal recordings on the Mac; evaluate on held-out sessions, including setup, rest and unrelated wrist movements. Compare a simple local signal-processing baseline before adding a model. Keep inference on Watch/iPhone and exclude recordings from cloud backup/sync unless the user explicitly chooses it. A phone replay can show a time axis, gaps, proposed repetition markers and edited/confirmed counts; it must never imply a reconstructed body pose, measured weight or certified safe technique.

## Implemented Build 6 prototype

- Settings opt-in defaults off and syncs to Watch. Start/Stop remains explicit, with only dumbbell curl and lateral raise choices. The Watch checks motion availability and HealthKit authorization, then starts its own strength-training workout session. It requests no Health reads, creates no workout builder, and saves no Health workout. System workout indicators/activity side effects are disclosed.
- Rotation-rate samples carry delivered Core Motion timestamps; the requested rate is 25 Hz. A 3-minute/4,500-sample cap, checkpoints roughly every two seconds, bounded 20-record library and main-thread publication only at checkpoints limit work. This is an engineering bound, not measured battery reliability.
- Stopped files transfer locally through WatchConnectivity. The Watch keeps originals; duplicate file delivery cannot overwrite an iPhone-confirmed count. Local raw files are excluded from cloud backup. Phone replay distinguishes raw trace, missing-sample gaps, proposed markers and a separately saved user-confirmed count.
- Peak detection is a simple unvalidated signal-processing hypothesis. No Core ML model is trained or deployed. Synthetic unit fixtures exercise code invariants only and are never claimed as personal training data or physical accuracy evidence.
- Relaunch preserves interrupted raw files and labels them interrupted. Cleanup ends only the session this process started. Unconditional recovery-and-end was deliberately omitted because ownership of a recovered HealthKit workout was not established. Interrupted system workout cleanup and real background behavior still need physical validation.
- Main Watch HealthKit entitlement and launcher profiles signed successfully using the existing free team; both installed in place. Local evidence: `.verification/upgrade-6/signing-verification.json` and `BuildLogs/upgrade6-device-refresh.log`.

## Remaining gate

A physical opt-in pilot must establish uninterrupted sampling with the wrist lowered, app switching, permission denial, interruption/recovery and a realistic workout duration, then measure power and error rates on suitable movements. The signed probe proves entitlement availability only. A short physical motion stream has now been observed (see below); background continuity, repetition accuracy and battery cost are not established. Native replay rendering/confirmation can be tested with explicitly synthetic simulator fixtures; that does not validate the sensor pipeline. Until that evidence exists, motion stays out of normal workout logging and the observation feature remains fully usable.

### Usability and permission follow-up

The user’s first physical attempt created no raw recording. After the screen was simplified, the user reported the Workouts-authorization error. The old message did not distinguish denied access from setup still pending; the corrected message does and points to Watch Settings → Health → Apps → Little Lift. This Apple-controlled permission cannot be enabled remotely. [Apple documents Watch Health app controls here](https://support.apple.com/en-us/104997).

Exercise selection moved to iPhone, Watch Start/Stop/Send stays fixed, and permission waits/cancellation/no-sample failures have visible feedback. The final motion layout was inspected at normal and xxxLarge text on the paired 46 mm simulator. Free signing and installation are verified. The user enabled Workouts access in Watch Health settings, then reported that Start recorded seconds and Stop worked. Read-back of the stopped file confirmed 587 samples spanning 23.3929 seconds, median delivered interval 0.03992 seconds and no interval above 0.16 seconds. Start/end battery both reported approximately 90%; this coarse short-run result cannot estimate battery cost. Wrist position and known repetition ground truth were not recorded, so wrist-down reliability and counting accuracy remain unverified. Start and stop cues were subsequently added behind the existing haptics preference. Their physical feel is not claimed.

Stopped recordings are queued only after the raw file is saved. Opening the motion screen retries a retained stopped file; Watch keeps its original and iPhone receive is idempotent. Send remains available if queueing fails. No automatic sensor capture was added. After the final update, opening the saved motion screen queued the real stopped recording and the real iPhone received it. Read-back matched the complete original record, including all 587 samples. Relaunching the Watch screen retained one iPhone record; that observation alone does not establish a second transport callback. Duplicate import behavior is covered separately by repository tests.
